# Surika 知识处理规则 · 讨论稿

**适用范围。** 当用户要求从会话、口述、代码、文档或项目经历中沉淀、读取、关联或修正知识时，遵守以下规则。根据当前任务自行决定如何理解材料、是否提问以及采用何种表达方式。用户只想记录一句话时，一句话也可以是完整的结果。

### 1. 保存对以后有用的最小陈述

优先保留能帮助以后理解用户技术背景、调用项目经验、辨别概念差异或重建设计取舍的内容。陈述应具体到可以单独理解，同时保留必要上下文。用户说“我熟悉 Java，日常用 Spring Boot”，可以按自述原意保存。只有某个细节会显著改变记录的含义或用途时，才值得追问。

### 2. 分清陈述对象与来源

让后续读者能够区分**技术上成立什么、项目中发生过什么、用户本人做过或表达过什么，以及 Agent 据此作出了什么推断**。保留足以辨认来源的线索，尤其是个人职责和判断的提出者。用户自述可以直接作为自述保存，无需先考核。Agent 给出的解释可以作为技术资料保留；将它归入用户已经理解的内容，需要来自用户的依据。

### 3. 让判断的范围与依据相称

分别看待接触过、实际操作过、解释过机制、比较过方案和在新情境中独立运用过。这些表现各自有价值，也可能只出现其中一种。用户能稳定完成操作，即使说不清原理，也应保留这项操作经验。提示、工具、版本或任务条件会改变判断时，一并保留。材料没有涉及的部分允许未知。

### 4. 每项关系都应表达一个可以理解的判断

建立联系时，说清两端**因为什么而相关**。可能是先修、因果、实现、对比、共同约束，也可能是一项经验在新条件下失效。关系的名称可以随内容选择，一句准确的话通常就够了。区分用户自己发现的联系、材料明确记载的联系和 Agent 提出的候选联系。采用类比且差异会改变结论时，指出哪一部分可以迁移、到哪里需要重新判断。找不到有意义的联系，就保留独立内容。

### 5. 使用已有记录时，以当前问题为准

只调用会实际改变当前帮助的内容。它可以让 Agent 略过已知基础、改用熟悉的术语、指出容易混淆的差异，或拿旧项目的一项约束来推演新问题。旧记录与用户当前说法冲突时，先检查时间、职责和情境。用户只要求直接解释时，照常解释；是否留下新的能力判断，取决于这次实际观察到了什么。

### 6. 分清学习进展、情境差异与记录错误

用户以前需要提示，后来能独立判断，可以记录为进展。同一个人在两个项目中作出不同选择，可能是约束变化，两段经验都应保留。若用户指出“那是同事设计的，我负责实施”，应修正原来的归属，并检查依赖它的摘要和关系。**用户纠正 Agent 对自己的误读，不能被写成用户刚刚学会了什么。** 用户可以查看、纠正或删除对自己的记录。

### 7. 向工具交付含义完整的结果

在用户授权的范围内，将结果交给负责相应操作的工具。交付内容遵循下面的最低要求，具体格式可以由工具约定。

| 交付的结果 | 接收方应能读出什么 |
|---|---|
| 一项知识或经验 | 陈述的对象和内容、依据或来源，以及影响理解的必要条件 |
| 一项关于用户的判断 | 用户表现或自述了什么，Agent 由此判断到什么范围，哪里仍然未知 |
| 一项关系 | 联系的两端、关系的具体含义、依据或提出者，以及会改变结论的边界 |
| 一次修正或删除 | 针对哪项已有记录、应怎样处理，以及哪些已有摘要或关系因此需要复核 |

只交付用户这次要求处理的部分。无需为了填满结构而补造细节，也无需为每份材料同时产生上述四种结果。

**用一个例子检验。** 用户说：“订单系统用了发件箱模式，我写了重试任务，当初的选型我没参与。”这段话已经足够沉淀一项有来源的经验。以后学习消息可靠性时，Agent 可以从用户实现过的重试任务切入。假如 Agent 当时还讲解了“为什么业务数据和待发消息要一起提交”，这段解释可以保留为参考；只有后来用户自己解释、预测或运用了这层关系，才有依据更新对其理解的判断。这样，同一份材料可以服务未来学习，也保留了**谁做过什么、谁理解了什么、哪些仍待了解**的区别。

这份草案主要从报告中的证据中心设计、情境认知、结构映射、概念转变和开放学习者模型推导。第 7 条是为 Surika 增加的工具交付约定。最值得用来审查整份规则的标准是：**换一个 Agent、换一类材料，它可以采用完全不同的抽取办法，但下一位读者仍能准确理解留下的内容，并有依据地修正它。** [理论参考模型](<deep-research-report (1).md>)
