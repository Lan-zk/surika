# Surika 专业知识积累与学习指导

工程设计草案 · 2026-11-25 · 供评审，尚未实现

## 当前讨论到了哪里

研究报告用于追溯概念、论文与理想目标。讨论已明确，关注对象包括用户的技术知识、架构理解、设计判断和项目经历；已有知识可以影响讲解起点、差异辨析及方案推导。用户提出了组合多项能力的方向。入口数量、职责、交互方式、记录位置、prompt、脚本及 CLI 均待设计。下文原型设想仅作比较材料。

## 先讨论一次真实使用会怎样发生

先以“了解已有技术背景 → 学一项新知识 → 用户有机会纠正理解”为例，比较下列交互。它们可以单独成立，需要弄清用户在哪些时刻愿意使用哪一种。

| 时刻 | 候选交互 | 需要弄清的问题 |
|---|---|---|
| 用户过去做过一个项目 | 主动讲一段经历；针对当前学习问题按需补充；或指定已有项目材料供阅读 | 用户愿意怎样开始？材料能说明系统如何设计，哪些信息还需本人说明才知道其职责？ |
| 学习中出现值得留下的信息 | 只在本次使用；由用户点名保存；或由 Surika 提出一句可修改的记录建议 | 哪些情况值得打断对话？用户怎样知道什么会留到下次？ |
| 用户带着新问题回来 | 直接按已知基础讲解；提一句采用了哪段经验；或先请用户判断旧经验是否适用 | 什么时候提醒会节省解释，什么时候会妨碍用户自己思考？ |
| 系统对背景判断有误 | 用户当场纠正；主动查看和修改积累的内容 | 如何让一次纠正影响后续学习？跨项目时用户预期哪些内容可见？ |

评审时先用同一个用户场景写出两种短对话，标出用户说什么、Surika 做什么、哪一步发生持久化，以及误判如何纠正。再按这些行为讨论交付形态：对话判断可以先试写成 prompt；可独立发起的任务是拆 skill 的理由；有确定输入输出、需可靠重复的操作才考虑脚本；存在直接从终端操作的需求时再评估 CLI。四者可以组合，现阶段没有选型结论。

## 从理想模型选择工程行为

[理论报告](<deep-research-report (1).md>)的“四层模型”给出了四个需要回答的问题。下表是本项目的设计选择。论文入口取自报告的长期阅读路线，供追溯设计理由；工程效果须由试点另行观察。

| 理论问题 | 首轮可实现的行为 | 检查依据 |
|---|---|---|
| 技术上什么成立？ | 涉及语言语义查相应规范，涉及某项目的设计动机回到设计记录或注明是谁的回忆。 | 能沿依据复核技术解释，用户过去的说法即使有误也可如实保留。[报告「综合理想型理论参考模型」](<deep-research-report (1).md>) |
| 对这个用户知道什么有何依据？ | 自述可直接用于选起点。需要判断独立能力时，回到具体任务、本人表现和当时得到的帮助。 | “项目用了 Oracle”“我写过查询”“我决定了索引策略”各自只支持相应范围的判断。[证据中心设计](https://doi.org/10.1002/j.2333-8504.2003.tb01908.x) |
| 旧经验怎样改变这次学习？ | 可略过先修、比较不同语义、借旧项目解释因果，或改变约束重新选方案。采用结构类比时，指出哪条关系成立、哪个条件变化后会失效。 | 能具体说出这条记录改变了哪一步。只有名词重合时直接讲新问题。[结构映射](https://doi.org/10.1207/s15516709cog0702_3) |
| 怎样知道判断需要更新？ | 用户愿意时，换一个问题请其解释、预测或作决策，记录帮助条件。用户纠正旧说法时，同步修正以后会读到的摘要。 | 能区分听过、提示后完成和换情境后独立运用。是否保持要留待后续观察。[报告命题 F、H](<deep-research-report (1).md>) |

报告还讨论了默会知识、远距类比检索和长期认知演化。首轮允许用代码操作或设计选择作为表现证据，允许把用户自己从多个项目中总结出的规律保留为有来源的判断。其余理想能力先作为观察方向。若实际材料不足以判断能力、遗忘或迁移，记录保持未知。

## 待比较的方案 A：两个入口共享记录

| 拟交付入口 | 用户意图与输出 | 独立使用条件 |
|---|---|---|
| 现有 `surika` | “帮我理解这个机制。”直接解释或陪用户推导；有相关记录时据此调整。对话里出现值得延续的专业经验，也可按同一约定保存。 | 零记录即可使用，只装教学包也可读已有记录。 |
| 拟增 `surika-background` | “整理我的技术栈／这个项目里我做过哪些设计。”从用户提供的叙述或指定材料中整理可复用的事实、个人职责和判断，支持查看与纠正。 | 仅装此包即可完成整理。用户只想列技术栈时，一句话也足够。 |

组合发生在数据上。两个入口各自按当前意图工作，先后读取同一目录即可；用户无需记住调用顺序。技术核验与讲解方法归教学包，采访和整理方法归背景包。共享部分限于记录的位置、含义、读取和修正规则。

**分发约束。** 当前安装单位是整个 skill 目录，用户可以只复制一个目录。建议沿用教学包的 `references/memory.md` 作为记录约定的维护源，在背景包中随包放置相同副本。修改时一起更新，发布前用文件比对检查一致。这样每个包都可独立移动，运行时只引用包内文件。出现第三个实际使用方或同步成本明显增加时，再评估生成步骤。[当前安装方式](../README-zh.md)

## 方案 A 的一种记录方式

沿用用户指定目录，缺省使用当前工作区的 `.surika/`。跨项目复用时，用户可为两个项目明确指定同一目录。全局安装 skill 只改变工作流的可用范围。首次保存说明路径，用户可拒绝、查看、修改和删除；遵循现有的 Git 忽略检查和不自动提交、同步或上传的约束。

- `state.md` 保留当前学习方向，另用少量带主题的相对链接指向值得复用的专业记录。现有文件缺少这些链接时照常续接。
- `records/` 继续存普通 Markdown。简短技术背景可以合并记录，项目经历按有意义的决策整理。保留日期、来源，以及本次确有的信息，如个人职责、项目约束、方案取舍、观察到的表现和提示。无需补齐字段。生活常识仅按当次交流需要使用。
- 先读索引，再读与当前问题相关的原文。判断相关性要看当前问题中的机制或约束。例如“谁负责重试”可指向另一个行业的重试决策，仅仅都叫“订单系统”不足以采用。找不到有用记录就直接教学。
- 再次整理同一经历时更新对应记录。若新旧说法冲突，保留来源与适用情境；用户已明确纠正的说法标明已替代，索引只指向当前结论。删除记录时移除相应索引与其中的个人摘要。旧格式按可读内容使用，无需批量改写。

**一条记录的完整用法（虚构示例）。** 用户说：“我在订单项目接过第二个支付渠道，按已有 Java 接口实现了适配器，接口是同事设计的。”背景包保存这句自述及项目线索，索引写“支付渠道接入、实现既有接口”。后来用户问 Go 接口放在哪个包，教学包可以从他熟悉的实现者角色切入，追问“如果订单模块只使用渠道的一项能力，谁最清楚该接口需要哪些方法？”若用户只要答案，直接解释即可。若他在新的通知渠道例子中自己给出了接口位置和理由，可追加此次表现以及是否得到提示。两条记录分别回答“以前做过什么”和“这次能怎样推理”。

## 若选择方案 A，可如何试作和验收

| 阶段 | 具体改动 | 进入下一阶段的条件 |
|---|---|---|
| 1 · 打通最小闭环 | 评审通过后记录用途变化的 ADR。扩展现有 memory.md，新增背景包的 SKILL.md 和随包记录约定；在教学包 SKILL.md 增加按需取用背景的触发条件。 | 在临时工作区用虚构经历跑通“整理 → 结束会话 → 新会话提问”，核对实际文件、被引用的原话及讲解改变之处。 |
| 2 · 检查行为和分发 | 在教学包 learning.md 补充关联选择、差异和反例；在中英文 README 说明两个入口的单独安装、组合和记录位置。用独立目录分别安装两包，再组合使用。 | 下面的工程场景逐项通过。至少在一个声明支持的宿主实测新会话加载；记录宿主、版本、安装方式和失败项，其他宿主单列验证状态。 |
| 3 · 观察实际价值 | 邀请自愿用户带一个真实项目经历和一个后续学习问题试用，留下去标识化的观察。用相同问题、相同宿主分别做有背景与无背景的讲解对照。 | 若记录确实改变起点、技术解释正确且用户认为有帮助，保留该用法。若经常错用背景、引入额外访谈或重复已知内容，优先修正触发和读取规则。 |

**工程验收场景**

| 给定情境 | 可观察的通过条件 |
|---|---|
| 仅装任一包，安装目录脱离仓库 | 用户能完成对应任务，文件引用可解析；两包内共享约定比对一致。 |
| 新用户直接提问，或老用户要求恢复普通开发 | 直接响应当前请求；无需背景访谈、建档或先完成练习。 |
| 已有相关记录、仅有表面相似记录、只有旧版学习记录 | 分别表现为据原文调整讲解、略过无关材料、正常续接。 |
| 用户自述熟悉技术，或在 Agent 给出方案后复述 | 可调整讲解起点；记录能明确区分自述、提示和独立表现。 |
| 用户纠正或删除记录，再开会话 | 新回答采用修正后的职责；删除项在记录和索引中均不再被检索到。 |
| 用户拒绝持久化、路径不可写、两个项目用了不同默认目录 | 分别验证无新增文件、明确告知保存失败仍可对话、背景不会意外串入另一项目。 |

工程验收只说明两个 skill 能按约定工作。学习效果需另看：隔一段时间，换一个约束不同的案例，用户在更少帮助下能否自行指出可复用的关系、说明失效条件并给出合理判断。试点同时记下错误迁移、提示次数和缺少后续观察的情况。少量真实案例能指导下一轮迭代，尚不足以作普遍因果判断。
